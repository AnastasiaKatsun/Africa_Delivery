# **6. Transition Architecture**

## **Принцип: обратимость и модульность**

Ключевой принцип переходной архитектуры — **модульный монолит**: система структурно разделена на модули с чёткими границами (Go-интерфейсы + внутренние REST-вызовы). Это позволяет выделять модули в отдельные микросервисы **без переписывания кода** — только физический переезд модуля в отдельный под Kubernetes.

Дополнительный принцип — **обратимость решений**: каждое архитектурное решение (ADR) спроектировано так, чтобы его можно было скорректировать без переписывания системы. Это касается и стратегии размещения данных (ADR-3), и выбора платёжного провайдера (ADR-4).

### **Ключевые решения на этом этапе**

1. **Архитектурный стиль** — модульный монолит на Go (ADR-1).
2. **Стратегия размещения данных** — гибридная: локальные VPS для Нигерии и Кении, GCP для ЮАР (ADR-3).
3. **Платёжные провайдеры** — прямые интеграции: Flutterwave (Нигерия), M-Pesa (Кения), Paystack (ЮАР) (ADR-4).
4. **Партнёры по логистике** — Sendbox (Нигерия), Sendy (Кения).
5. **Стратегия кеширования** — Redis + CDN (ADR-2).

* catalog
* order
* payment
* logistics
* notification
* seller
* analytics
* consent

Каждый модуль:

* Имеет чёткий интерфейс (Go interface).
* Общается с другими модулями через внутренние вызовы (в рамках процесса).
* Инкапсулирует свою схему данных в PostgreSQL (отдельные таблицы/схемы).
* Может быть выделен в отдельный микросервис без изменения кода — только конфигурация.

## **Состояние 3: 6 месяцев (Апрель 2027)**

### **Что меняется**

| **Изменение** | **Что именно** | **Как происходит (без переписывания)** |
| --- | --- | --- |
| **Выделение сервиса «Платежи»** | Модуль **payment** переносится в отдельный под Kubernetes | Модуль уже изолирован: у него своя схема в БД, свой интерфейс. Переезд = добавление HTTP/gRPC-обёртки и настройка сетевого взаимодействия. |
| **Выделение сервиса «Уведомления»** | Модуль **notification** становится отдельным микросервисом | Аналогично: модуль уже выделен, добавляем транспортный уровень. |
| **ЛК продавца** | Фронтенд-приложение (Vue/React) + API | Пишется с нуля как отдельное приложение, использует существующий API монолита. |
| **Модуль возвратов** | Новый модуль **refund** в монолите | Добавляется в монолит: новые таблицы, новые эндпоинты. Не влияет на существующую структуру. |
| **ЮАР (POPIA)** | Подключение Paystack, consent-manager | Consent-модуль уже встроен в монолит. Добавление ЮАР = конфигурация (новая схема БД, новый регион). |

**Что выделено:** **payment**, **notification**.

## **Что НЕ меняется на всём протяжении**

| **Элемент** | **Почему не меняется** |
| --- | --- |
| **Модульные границы** | Модули выделены с первого дня — выделение в микросервис не требует изменения кода |
| **API-контракты** | REST API стабильны — внешние интеграции (PWA, партнёры) не переписываются |
| **Схема данных** | PostgreSQL-схемы модулей остаются стабильными — миграция данных не требуется |
| **Стратегия кеширования** | Redis + CDN (ADR-2) — масштабируется добавлением узлов |
| **Consent Manager** | Встроен в ядро — новые страны = конфигурация |
| **Мониторинг** | Prometheus + Grafana + Loki + Jaeger — единый стек на всех этапах |
